Queries

Abbreviations used on this page (TSDB, WAL, TTL, HWM, XPUB, ZMQ, SQLite, JSON, CLI, API, RSS, fd, PEP, CORS, OBS...) are defined in the Abbreviations & jargon section.

Querying means asking for stored measurements, usually over a time range, sometimes with a summary (aggregation). You can query over the ZMQ REP socket (port 12502) or the HTTP gateway (port 12505). One thing to keep in mind: the two transports use different time units, described in the warning below.

Time units differ by transport. The ZMQ query path takes start/end in epoch nanoseconds; the HTTP gateway takes them in epoch seconds. Query results always return timestamps in seconds. Ingestion timestamps are seconds on both.

ZMQ request format

This is the raw JSON sent over the query socket. With the bundled Python client you normally do not build it yourself — it is shown here for completeness and for other languages.

{
  "type": "query",                    // optional — omitted is treated as a query
  "metric": "cpu.usage",             // required: non-empty string
  "start": 1720000000000000000,      // epoch NANOSECONDS (optional, inclusive)
  "end":   1720003600000000000,      // epoch NANOSECONDS (optional, inclusive)
  "aggregation": "avg",              // optional
  "interval": "15m",                 // optional bucket size
  "limit": 100,                      // optional, first N in the selected order
  "order": "asc"                     // optional: asc | desc
}

Notes:

  • Omitting start/end queries all time. Bounds are inclusive. A query with aggregation and no interval returns a single value over the whole window; with an interval it returns one value per bucket (buckets aligned to the Unix epoch).
  • There is no tag filter on the wire — a metric's data is queried as a whole. (Write tags to split a metric into series; only the embedded Python API can query by series_ids directly — see below.)
  • limit and order apply to the raw paths; results are ordered ascending (or descending with order=desc) and the first N are kept.
  • Server-side budget: queries are answered through a worker thread with a query.timeout_s budget (default 30.0; set to 0 to disable). A query that exceeds the budget gets QUERY_TIMEOUT back and the service stays responsive. The bundled client also applies its own 30s receive timeout and raises ClientError if no reply arrives in time.

Aggregation functions

FunctionDescription
avgAverage (arithmetic mean)
sumSum of values
minSmallest value
maxLargest value
countNumber of values
firstFirst value in the window/bucket
lastLast value in the window/bucket
medianMedian (middle value)
p9595th percentile: 95% of values are at or below this
p9999th percentile: 99% of values are at or below this

Percentiles use rank interpolation: for a sorted list of n values, the q-th percentile sits at rank (n-1) * q and is linearly interpolated between the two neighbours. Empty windows — a window with no data — behave differently by endpoint: on the /api/v1/aggregate (and ZMQ aggregations) paths, count and sum return 0.0 and every other function returns NaN (serialized as null); on the single-function paths (/read?aggregation=… and ZMQ aggregation) an empty window returns data: [].

Intervals

An interval is a number plus a unit: s (seconds), m (minutes), h (hours), d (days). Examples: 5s, 1m, 15m, 1h, 1d. Buckets start at Unix-epoch boundaries (ts // bucket_ns * bucket_ns).

Multiple whole-window aggregations

Send aggregations (a comma-separated string) instead of aggregation to get several values over one window. The reply's data becomes a dict of function → value instead of a list:

{
  "type": "query",
  "metric": "cpu.usage",
  "aggregations": "avg,min,max,p95"
}
# → {"status":"ok","data":{"avg":0.71,"min":0.4,"max":0.98,"p95":0.91}}

Response format

{
  "status": "ok",
  "data": [
    {"timestamp": 1720000000.0, "value": 0.72},   // seconds
    {"timestamp": 1720000060.0, "value": 0.68}
  ]
}

For a whole-window aggregation (no interval) the single result row is anchored at the window's oldest sample (the last one when order=desc). For an aggregations (multi-func) query, data is {func: value}.

HTTP queries

HTTP is the easiest path from scripts, browsers, and languages without a ZMQ binding. Timestamps are in seconds here; results are identical in shape to the ZMQ path.

EndpointParamsReturns
GET /api/v1/read metric (required), start, end (seconds), aggregation, interval, limit (1–100000), order (asc|desc) {"status":"ok","data":[{timestamp,value}]}
GET /api/v1/aggregate metric (required), start, end (seconds), funcs (comma list, default avg) {"status":"ok","aggregations":{func:value}}
GET /api/v1/stats — {"status":"ok","metrics":N,"series":M}
curl "http://127.0.0.1:12505/api/v1/read?metric=cpu.usage&aggregation=avg&interval=15m"
curl "http://127.0.0.1:12505/api/v1/read?metric=cpu.usage&start=1720000000&end=1720003600&limit=10&order=desc"
curl "http://127.0.0.1:12505/api/v1/aggregate?metric=cpu.usage&funcs=avg,min,max,p95"
curl "http://127.0.0.1:12505/api/v1/stats"
curl "http://127.0.0.1:12505/api/v1/health"

Bad parameters (limit outside 1–100000, invalid order, missing metric, non-numeric start/end) are rejected with 422; an unknown aggregation, or an invalid interval used together with an aggregation, with 400.

Examples

For every classic question phrased the way a person asks it ("average CPU last hour?", "peak temperature yesterday?", "99th percentile over the week?"), see the runnable question catalog — examples/question_examples.py seeds data and answers 13 such questions with machine-readable output. The building blocks below are the same ones it uses.

Last hour of raw data (Python client)

from sqtseries import Client
import time

c = Client()
now_ns = time.time_ns()
rows = c.query("cpu.usage", start=now_ns - 3600 * 10**9, end=now_ns)

Per-minute averages

c.query("cpu.usage", aggregation="avg", interval="1m")

Daily max over the last week

c.query("cpu.usage", start=now_ns - 7 * 86400 * 10**9, end=now_ns,
        aggregation="max", interval="1d")

Raw ZMQ query

import zmq, orjson

ctx = zmq.Context()
sock = ctx.socket(zmq.REQ)
sock.setsockopt(zmq.LINGER, 500)
sock.setsockopt(zmq.RCVTIMEO, 30000)
sock.connect("tcp://127.0.0.1:12502")
sock.send(orjson.dumps({
    "type": "query", "metric": "cpu.usage",
    "start": now_ns - 3600 * 10**9, "end": now_ns,
    "aggregation": "avg", "interval": "1m",
}))
reply = orjson.loads(sock.recv())
print(reply)

HTTP (seconds)

curl "http://127.0.0.1:12505/api/v1/read?metric=cpu.usage&start=1720000000&end=1720003600&aggregation=avg&interval=1m"

Querying by series_id (embedded API)

Each unique (metric, tags) pair is a series. The embedded Python API can query a specific series directly — the wire protocol cannot (it has no tag filter). This path uses the clustered primary key (series_id, timestamp_ns) and is the fastest way to isolate one host:

from sqtseries.engine import StorageEngine, create_sqlite_engine, initialize_schema
from sqtseries.query import TimeSeriesDB

engine = create_sqlite_engine("~/.sqtseries/data/db.sqlite")
initialize_schema(engine)
tsdb = TimeSeriesDB(StorageEngine(engine))

sids = tsdb.store.series_ids_for_metric("cpu.usage")
rows = tsdb.query(series_ids=[sids[0]], start=now_ns - 3600 * 10**9, end=now_ns)

To answer per-tag questions (which host is hottest? which room is busiest?), map each series_id back to its tags and query the ones you care about:

import orjson

sids = tsdb.store.series_ids_for_metric("cpu.usage")
by_host = {}
for sid in sids:
    _, tags_json = tsdb.store.get_series_meta(sid)
    tags = orjson.loads(tags_json) if tags_json else {}
    by_host.setdefault(tags.get("host", "untagged"), []).append(sid)

# the two web hosts only — per-series averages in one clustered-PK pass
target = [sid for host, sids_ in by_host.items() if host.startswith("web") for sid in sids_]
rows = tsdb.query(series_ids=target, start=start_ns, end=end_ns)
for host, sids_ in by_host.items():
    rows = tsdb.query(series_ids=sids_, start=start_ns, end=end_ns)
    avg = sum(v for _, v in rows) / len(rows) if rows else 0
    print(f"{host}: avg {avg:.2f}")

The same pattern works with any tag key. See Tags: why and how for when to use tags and cardinality guidance, and the runnable examples/tags_examples.py.

Gap filling (embedded API)

The embedded query API supports linear interpolation of small gaps (fill_gaps_ns inserts a midpoint between two samples when the gap is at most that size):

# fill gaps <= 60s by inserting a midpoint value
rows = tsdb.query("cpu.usage", start=..., end=..., fill_gaps_ns=60 * 10**9)

downsample_to_intervals(..., fill_missing=True) (in sqtseries.query.agg) emits NaN buckets for empty intervals instead of skipping them. Both are embedded-only conveniences — there is no wire parameter for them.

NaN and infinity values

Non-finite values (NaN, ±Inf) are rejected at ingest on both paths (ZMQ: dropped and counted invalid; HTTP: 400 "value must be finite"). They can however be returned: empty-window aggregate results are NaN, serialized as null.

The rollup fast path

Wide-window aggregates can be answered from the hourly rollup table instead of scanning every raw row. The exact eligibility rules:

  • Eligible when the aggregation is avg, sum, min, max, or count (the functions expressible from the rollup's count/sum/min/max columns).
  • The interval, if given, must be a whole-hour multiple (1h, 2h, 1d, …); non-hour intervals (1m, 30m, 90m, …) fall back to raw rows.
  • The window must span at least two completed hours and its end-hour boundary must be at or below the rollup watermark (which tracks the last completed, rolled hour) — i.e. the window's tail cannot reach into the current hour.
  • Not eligible: first, last, median, p95, p99; non-whole-hour intervals; windows shorter than two completed hours.
  • Always exact. Only completed hours are rolled, and the in-progress hour is read from raw rows and merged — the rollup is an acceleration, never an approximation.

Measured effect (benchmarks, 2M rows at 20K points per series): the same wide-window query drops from ~13ms linear (raw scan) to ~1.3ms near-constant (~10x). The rollup runs in the background (rollup.interval, default every 5 minutes); hours are only rolled once they are at least the client-skew window past completion.
