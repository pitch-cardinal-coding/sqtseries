Data Ingestion

"Ingestion" is the word for getting data in. Two transports accept the same JSON measurement object:

TransportEndpointBehaviour
ZMQ PUSH tcp://127.0.0.1:<ingest> (default 12501; auto-detected — see below) Fire-and-forget. One frame per measurement, no acknowledgement, no ZMQ-level batching.
HTTP POST http://127.0.0.1:12505/api/v1/write Acknowledged. Accepts one object or an array; replies {"status":"ok","written":N}.

All sockets bind to 127.0.0.1. The ingest port is the only auto-detected one. With ports.auto_detect on (the default) the service scans 12500–12700 and binds the first free port — usually 12500, not the configured 12501. The configured 12501 is used only when auto_detect = false. sqtseries ports shows the live set and sqtseries status prints them next to the pid.

Time units. Ingestion timestamps are Unix epoch seconds (integer or float) and are converted to nanoseconds by the server. Query start/end are nanoseconds on the ZMQ query path and seconds on the HTTP gateway; query results always carry seconds.

The message shape

A measurement is a small JSON object. Only metric and value are required:

{
  "metric": "cpu.usage",
  "tags": {"host": "web1", "env": "prod"},   // optional
  "value": 0.72,
  "timestamp": 1720000000.123                // optional epoch SECONDS
}
FieldTypeRequiredDescription
metricstringYesMetric name (any non-empty string; dots are conventional, not enforced)
valuenumberYesNumeric value (int or float; boolean is rejected; must be finite — no NaN or ±Inf)
tagsobjectNoString → string dimensions. Each unique (metric, tags) pair becomes a series
timestampnumberNoUnix epoch seconds (float allowed). Defaults to the server clock

Unknown extra fields are ignored.

ZeroMQ ingestion (PUSH)

Connect a PUSH socket to tcp://127.0.0.1:12501. Each message is exactly one measurement; sends are fire-and-forget — there is no reply, so a send that completes has reached the socket, not the database.

import zmq
import orjson

ctx = zmq.Context()
sock = ctx.socket(zmq.PUSH)
sock.setsockopt(zmq.SNDHWM, 10000)
sock.setsockopt(zmq.LINGER, 500)     # flush queued messages on close
sock.connect("tcp://127.0.0.1:12501")

sock.send(orjson.dumps({"metric": "cpu.usage", "tags": {"host": "web1"}, "value": 0.72}))

Send each point as one frame; there is no ZMQ-level batching and the server handles each message individually. Invalid messages (bad JSON or bad fields) are dropped and counted — they are never acknowledged and never stored.

metrics = [
    {"metric": "cpu.usage", "tags": {"host": f"web{i}"}, "value": 0.7 + i * 0.01}
    for i in range(1000)
]
for m in metrics:
    sock.send(orjson.dumps(m))

Use the bundled client for a managed socket. write() and write_many() send the same one-frame-per-measurement layout:

from sqtseries import Client
c = Client()
c.write("cpu.usage", 0.72, {"host": "web1"})
c.write_many([
    {"metric": "cpu.usage", "value": 0.72, "tags": {"host": "web1"}},
    {"metric": "mem.usage", "value": 512.0, "tags": {"host": "web1"}},
])

HTTP ingestion

POST /api/v1/write accepts a single object or an array. A batch is validated before any insert: if one item is bad, the whole request fails with 400 and nothing is written — safe to retry. The response says how many were written.

curl -X POST http://127.0.0.1:12505/api/v1/write \
  -H "Content-Type: application/json" \
  -d '{"metric":"cpu.usage","tags":{"host":"web1"},"value":0.72}'
# {"status":"ok","written":1}

curl -X POST http://127.0.0.1:12505/api/v1/write \
  -H "Content-Type: application/json" \
  -d '[
    {"metric":"cpu.usage","tags":{"host":"web1"},"value":0.72},
    {"metric":"cpu.usage","tags":{"host":"web2"},"value":0.68}
  ]'
# {"status":"ok","written":2}

An invalid body returns 400 with a message naming the problem — see Error codes for the full list (non-empty string metric, numeric finite value, string→string tags, numeric timestamp).

Timestamps and clock skew

If you omit timestamp, the server stamps the measurement with its own clock — recommended, since it avoids clock differences on the sending machine. If you do send a timestamp, it must be within ingestion.reject_client_timestamp_skew_s (default 300s) of the server clock; anything further out is rejected:

  • HTTP: the write fails with 400 and "client timestamp skew exceeds 300.0s".
  • ZMQ: the message is dropped and counted in the invalid admin stat — the PUSH path never replies.

The guard also keeps the hourly rollup consistent: data arrives in (near) chronological order, and an hour is only rolled once it is at least this far past completion, so a late write can never land in an already-rolled hour.

Error handling

  • On ZMQ there is no per-message acknowledgement. Invalid messages (JSON parse errors, missing metric, non-numeric value, non-finite values, rejected skew) are dropped and counted — see invalid (and ingest_errors) in the admin stats reply.
  • Frames larger than ingestion.max_message_size (default 50 MiB) are dropped at the socket level — the peer is disconnected — and never ingested.
  • The PUSH socket HWM (default 10000) provides natural backpressure: when the send queue is full, a blocking send() blocks instead of silently losing data.
  • On HTTP every failed write is a 400 with a message; a multi-item batch fails as a whole.

Performance

On the wire path every accepted message is written to SQLite immediately (there is no batching queue); throughput is dominated by the storage layer. Engine-level measurements with batched inserts (scripts/benchmark.py) are on the benchmarks page: roughly ~65K–253K rows/sec depending on dataset size, page-cache-bound up to ~1M rows and disk-bound beyond. Run the benchmark on your own machine if you need numbers for your hardware.
