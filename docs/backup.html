Backup, Restore & Vacuum

sqtseries keeps everything in one SQLite file. That makes backup simple, restore trivial, and — because databases grow — occasional vacuuming worth understanding. This page covers all three.

1. What to back up

Your data lives in exactly one place: the database file configured by database.path (default ~/.sqtseries/data/db.sqlite). Back up that file. Everything — the series table, every monthly measurements partition, and the hourly rollup summaries — is inside it.

Never copy db.sqlite alone while the service is running. In WAL mode, recent writes live in the companion db.sqlite-wal file until a checkpoint writes them into the main file. A plain file copy at an arbitrary moment can silently miss committed-but-uncheckpointed data. Always use a proper backup instead (below), which reads through the WAL and is always consistent.

The database folder

Alongside db.sqlite you may see:

FileWhat it isDo you back it up?
db.sqliteThe database itself Via a proper backup, yes. Never a bare copy while running.
db.sqlite-walWrite-ahead log holding recent committed writesNot separately — a proper backup reads through it. A bare copy would need this file too, and even then only if the service is stopped.
db.sqlite-shmShared-memory index for the WALNever. Recreated automatically.
runtime.jsonPID + ports of the running serviceNever. Recreated on start.

2. How to back up

Backups are consistent point-in-time snapshots taken with SQLite's VACUUM INTO — safe even while writes are in flight. Each backup is a single standalone .db file you can open with any SQLite tool.

Automatic (scheduled)

By default the service takes a snapshot on startup and then every backup.interval (default 24h). To change or disable it:

# config.toml
[backup]
enabled = true
interval = "24h"              # how often a snapshot is taken
path = "~/.sqtseries/backups/"

The first pass runs immediately at startup, then once per interval. A snapshot younger than the interval is skipped, so restarts do not pile up duplicate backups. The newest snapshot is reported in admin stats as last_backup; backup_runs and backups_created track the scheduler.

On demand

# CLI — one snapshot, prints the path
sqtseries backup

# Admin command (ZMQ REP, port 12504)
{"cmd": "backup"}      # -> {"status":"ok","path":"..."}

# Python client
c.admin("backup")

Backup file naming

Backups are written to backup.path as sqtseries-YYYYMMDD-HHMMSS.db, e.g. sqtseries-20260808-171500.db. Two backups in the same second collide (a BackupExistsError, skipped silently by the scheduler). There is no built-in rotation or deletion of old backups — prune them yourself with your usual file tools, e.g. keep only the newest N files (delete lines N+1 onwards): ls -t ~/.sqtseries/backups/*.db | tail -n +$((N+1)) | xargs rm.

3. How to restore

There is no restore command — restoring is pointing sqtseries at a backup file. A backup is a complete database, so it starts, migrates, and serves exactly like any other:

# 1. Stop the service that owns the database you are replacing
sqtseries stop

# 2. (Optional) keep a copy of the current state
cp ~/.sqtseries/data/db.sqlite ~/db-before-restore.sqlite

# 3. Point a config at the backup file and start
# config.toml
[database]
path = "/path/to/sqtseries-20260808-171500.db"

sqtseries --config config.toml run

On startup the service runs any pending migrations, creates the current monthly partition if the backup predates it, checks integrity, and switches the file to WAL mode. The backup file itself is not modified; the service works on it in place (WAL files appear next to it once running).

Restoring to a new machine — copy the backup file to the new machine, set database.path to it, and run. That is the whole procedure: one file, one setting. The default ports, admin socket, and everything else come up normally.

4. Vacuum: what it is, when and how to run it

VACUUM rewrites the entire database file into a compact form, reclaiming space from deleted rows and dropped partitions.

Why the file grows

sqtseries drops expired monthly partitions automatically (retention, default 30 days) and deletes data as you prune it. Those pages are freed to SQLite's internal freelist — the space is reusable but the file does not shrink, because the database is set to auto_vacuum = INCREMENTAL (set once when the file is created). The file stays at its historical peak size until you vacuum it. WAL checkpointing (background, at 64 MB) truncates the -wal file — it never shrinks the main database file.

When to run it

  • After heavy pruning or retention drops, when you want the disk space back.
  • Periodically as part of maintenance (weekly/monthly is plenty for most workloads).
  • When the file size matters (backups, moving machines, quotas).

How to run it

# CLI — full VACUUM (recommended; stop the service first)
sqtseries stop
sqtseries vacuum          # prints "VACUUM complete"
sqtseries run

VACUUM needs exclusive access to the file. A live service's concurrent reads and writes usually block it. The admin command exists for small maintenance, but it often fails while the service is busy:

# Admin command — may fail with VACUUM_BUSY while running
{"cmd": "vacuum"}    # -> {"status":"ok","vacuumed":true}
                     # or {"status":"error","error":{"code":"VACUUM_BUSY",...}}

The offline sqtseries vacuum (service stopped) is the recommended path for anything larger than a quick tidy.

Backup vs vacuum — don't confuse them

VACUUM INTO (backup) VACUUM (vacuum)
Creates a fileYes — a standalone snapshot No — rewrites the existing file in place
Needs the service stoppedNo — safe while running Yes (recommended)
Shrinks the databaseNo (source untouched) Yes
Use forBackup, restore, moving machines Reclaiming disk space

5. Storage layout summary

~/.sqtseries/
├── data/
│   ├── db.sqlite          # the database — everything lives here
│   ├── db.sqlite-wal      # WAL (recent writes; checkpointed automatically)
│   ├── db.sqlite-shm      # WAL index (recreated)
│   └── runtime.json       # pid + active ports (recreated)
└── backups/
    └── sqtseries-YYYYMMDD-HHMMSS.db   # consistent snapshots

Everything you need to back up is one folder; everything you need to restore is one file.
