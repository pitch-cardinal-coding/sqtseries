Live Streaming

Besides storing data, sqtseries republishes every accepted measurement live to subscribers, over the ZMQ XPUB socket (port 12503) and the WebSocket gateway (port 12505). Streaming is best-effort: a slow subscriber misses messages rather than delaying the sender. For a copy of data you can rely on, use a query afterwards or send data over your own reliable transport.

Message format

Each publication is a two-frame ZMQ message: [topic, json-payload]. The topic is exactly the metric name, and the payload carries the measurement as accepted:

# topic:  cpu.usage
# payload:
{"metric": "cpu.usage", "tags": {"host": "web1"}, "value": 0.72}
The streamed payload has no timestamp field — it is the measurement as accepted. Use the timestamp the server assigned (visible in queries) when you need one. Only measurements that pass validation are published; dropped (invalid) messages are never streamed.

ZeroMQ SUB

Connect a SUB socket to tcp://127.0.0.1:12503 and subscribe to a topic prefix. ZMQ SUB uses prefix matching on the topic bytes:

FilterMatches
b""All metrics
b"cpu."All metrics starting with cpu.
b"cpu.usage"Exactly the cpu.usage topic (and any longer topic)
import zmq

ctx = zmq.Context()
sock = ctx.socket(zmq.SUB)
sock.setsockopt(zmq.LINGER, 0)
sock.connect("tcp://127.0.0.1:12503")
sock.setsockopt(zmq.SUBSCRIBE, b"cpu.")   # prefix match

while True:
    topic, data = sock.recv_multipart()
    print(topic.decode(), data.decode())

The socket is an XPUB on the server side: it receives subscribe and unsubscribe events directly from the wire, so subscriber counts are exact at any moment (see the subscribers admin command). A disconnecting subscriber's topic stays counted as "lingering" for streaming.linger_seconds (default 30s) before it is cleaned up.

Bundled client

from sqtseries import Client

c = Client()
for payload in c.subscribe("cpu."):
    if payload is not None:      # None = idle heartbeat every ~0.5s
        print(payload)

subscribe(topic="*", timeout=0.5) polls with a timeout and yields None as a heartbeat while idle, so the loop can exit cleanly (for example on shutdown) without blocking forever in recv().

WebSocket

ws://127.0.0.1:12505/ws/subscribe?metric=cpu. — the metric parameter is a single topic prefix (* or omitted for all). It is not a comma-separated list, and the path is /ws/subscribe (not under /api/v1). The server sends a {"type":"ping"} keepalive message when no measurement has arrived for 30 seconds.

# websocat
websocat "ws://127.0.0.1:12505/ws/subscribe?metric=cpu."

# JavaScript
const ws = new WebSocket("ws://127.0.0.1:12505/ws/subscribe?metric=cpu.");
ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  if (msg.type === "ping") return;
  console.log(msg);   // {metric, tags, value}
};

For live connection/subscription monitoring, the gateway also exposes a push-only feed at ws://127.0.0.1:12505/ws/connections: it sends a {"type":"snapshot",...} on connect, then one frame per change — {"type":"conn",...,"connected":true/false} for WebSocket clients (with connected_at/left_at arrival and leaving times) and {"type":"sub",...} for ZMQ subscribers (with arrived_at/left_at and first_seen). The camera dashboard's "Connected clients" / "ZMQ subscribers" / "Activity" panels render this feed. New connections beyond http.max_websocket_connections close with code 1013; a subscriber that cannot accept a frame within 30s is closed with 1011; inbound frames over 16 MiB close with 1009.

Stats events (port 12506)

Connection and subscription changes are emitted on a separate ZMQ PUB socket (port 12506). Any ZMQ SUB client can consume them with prefix filters (b"conn", b"sub", b"report", or b"" for all):

TopicFieldsWhen
connconnect: id, kind ("ws"), peer, topic, connected_at, connected: true, ttl (60)
disconnect: id, kind, peer, topic, connected: false		 A WebSocket client connects or disconnects
subjoin: kind ("zmq"), topic, subscribers, ttl (30);
leave: kind, topic, subscribers (no ttl)		 A ZMQ SUB subscriber joins or leaves a topic
reportuptime_s, ws_connections, zmq_subscribers, active_topics Every 10 seconds, for monitoring dashboards
import zmq, json

ctx = zmq.Context()
sub = ctx.socket(zmq.SUB)
sub.connect("tcp://127.0.0.1:12506")
sub.setsockopt(zmq.SUBSCRIBE, b"conn")  # or b"" for all events

while True:
    event_type, payload = sub.recv_multipart()
    data = json.loads(payload)
    print(f"{event_type.decode()}: {data}")

Delivery guarantees

  • PUB/SUB does not retransmit. A subscriber that connects late or reads too slowly misses whatever it did not receive.
  • The gateway's SUB socket applies a receive HWM of 1000 frames (slow WebSocket readers drop).
  • For reliable delivery, use the HTTP/REQ query path or an ingestion pipeline you control.
