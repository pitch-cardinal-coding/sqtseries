Camera analytics: pumping a metrics feed and answering everything

A camera with edge analytics streams JSON over a WebSocket — people and vehicle counts, per-minute rates, battery and CPU telemetry. sqtseries stores each number as a flat measurement tagged with the camera ID, and once data accumulates you can answer questions like what was the busiest hour?, how fast is the battery draining?, and does heavy footfall load the CPU?

How it works

One message from the feed (about 4 per second) looks like this:

{
  "camera_id": "test_cam_001",
  "generated_at": "2026-08-08T16:26:30.33+00:00",
  "current_visible_people": 21,
  "total_detected_people": 150,
  "current_visible_cars": 6,
  "total_detected_vehicles": 81,
  "people_last_minute": 20,
  "cars_last_minute": 6,
  "system_metrics": {
    "batteryPercent": 84.3,
    "batteryTemperature": 28.9,
    "cpuUsagePercent": 38.5,
    "cpuTemperature": 63.8
  }
}

sqtseries stores flat metric + value + tags, so camera_feed.py flattens each message into 11 measurements, all tagged with camera_id=test_cam_001:

traffic.people.current        21      camera_id=test_cam_001
traffic.people.total          237     camera_id=test_cam_001
traffic.vehicles.current      9       camera_id=test_cam_001
traffic.vehicles.total        100     camera_id=test_cam_001
traffic.people.last_minute    21      camera_id=test_cam_001
traffic.cars.last_minute      9       camera_id=test_cam_001
system.battery.percent        84.3    camera_id=test_cam_001
system.battery.temperature    28.5    camera_id=test_cam_001
system.cpu.usage              41.3    camera_id=test_cam_001
system.cpu.temperature        62.4    camera_id=test_cam_001
status.detection_overlay      1       camera_id=test_cam_001

String fields (battery health, footer text, overlay URLs) are not numeric and are skipped. All points of one message are written in a single HTTP batch, which keeps the writes well under the default rate limit.

Live dashboard

The simulator also serves a live web page at the same port — open http://<host>:<port>/ (or /overlay.html) in any browser. The page connects to the same-origin metrics WebSocket and renders each reading as it arrives: people and vehicle counts, per-minute rates, battery charge/temperature/ health, CPU usage/temperature, and the detection-overlay status — with a connection badge that auto-reconnects if the simulator restarts. It is a single self-contained file (examples/camera/overlay.html, no external assets), so it works offline on a LAN and can be dropped into an OBS browser source. The dashboard reads the raw feed only; it does not touch sqtseries. It uses inline CSS/JS by design (it is a trusted, developer-owned artifact with no user input) — the sqtseries HTTP gateway, by contrast, serves strict security headers on every response.

Also subscribing to the time-series database

Give the page a ?sqtseries= parameter pointing at the /ws/subscribe endpoint of a running sqtseries instance and it adds a Time-series DB card that streams what the database publishes back to the same page — the last reading per metric, with its tags and age, plus a frame counter and its own auto-reconnecting connection badge. HTTP writes to /api/v1/write are broadcast to live subscribers just like ZMQ ingests, so with the camera feed pumping, this card confirms the whole loop: camera → overlay WebSocket → sqtseries → page. An optional &metric=<prefix> filters to one topic prefix (default *).

# camera page + live sqtseries stream (sqtseries default HTTP port 12505)
# <port> is the simulator's printed WebSocket port (random by default)
http://<host>:<port>/overlay.html?sqtseries=ws://<host>:12505/ws/subscribe&metric=traffic.

# when started by examples/camera/sqtcam.sh (HTTP port 17105)
http://<host>:<port>/overlay.html?sqtseries=ws://<host>:17105/ws/subscribe

Without the parameter the card shows a "not configured" hint and the page makes no connection attempts, so it stays usable as a pure overlay.

Live subscribers, clients, and activity

The DB card also shows, in real time, who is connected to sqtseries — by watching the push-only /ws/connections feed (no polling): a Connected clients table of active WebSocket subscribers (kind, peer, topic, arrival datetime, connected-for), a ZMQ subscribers table (topic, count, since), and an Activity log of every join and leave with its YYYY-MM-DD HH:MM:SS timestamp and duration. Arrival and leaving times come from the feed itself: conn events carry connected_at and (on leave) left_at; sub events carry arrived_at/left_at and first_seen. Joins and leaves are pushed the instant they happen.

# validate the feed end to end against a running sqtseries (joins/leaves,
# exact counts, arrival/leaving times, push latency)
python3 examples/camera/conn_validate.py \
    --host 127.0.0.1 --http-port 12505 --stream-port 12503
# ...connects 3 WebSocket clients + 2 ZMQ subscribers, joins/leaves them, and
# prints each event's latency; exits non-zero on any mismatch

examples/camera/conn_validate.py is the same harness the test suite runs (tests/test_websocket_edge.py, tests/test_camera_overlay_page.py), so the page's live figures and the server's registry always agree.

Running the full pipeline

The repository includes a simulator (overlay_server.py) that generates this feed on a random free port, so the whole flow works end to end without any camera hardware. The one-command runner (examples/camera/sqtcam.sh) starts everything in a single tmux session — ideal for leaving overnight to accumulate data:

# one command: sqtseries + simulator + camera feed in a tmux session
python3 examples/camera/sqtcam.sh        # or: bash examples/camera/sqtcam.sh
tmux attach -t sqtcam             # watch the three windows live
tmux kill-session -t sqtcam       # stop everything (data persists)

# anytime — answer every question from the stored data
python3 examples/camera/camera_feed.py --ask --host 127.0.0.1 --http-port 17105

sqtcam.sh starts three windows: sqtseries (the service, config at /tmp/sqtcam/conf.toml, ports 17101–17106), overlay (the simulator), and camera (the feed, wired to the simulator's random port automatically). It refuses to start a second session if one is already running.

Without the runner, the same flow works in four terminals:

# terminal 1 — the data source (note the printed WebSocket URL)
python3 examples/camera/overlay_server.py

# terminal 2 — sqtseries
sqtseries --config config.toml run

# terminal 3 — pump the feed into sqtseries
python3 examples/camera/camera_feed.py --ws ws://localhost:<port>/ws/metrics
#   let it run for a few minutes (or hours/days for real data)

# terminal 4 — answer every question from the stored data
python3 examples/camera/camera_feed.py --ask

--ask runs 17 questions: traffic levels and percentiles, busiest hour and day, total footfall, day-over-day trend, pass-through turnover, anomaly vs the same hour on previous days, battery drain rate and time-to-empty projection, CPU and thermal profile, footfall/CPU correlation, feed staleness and uptime, per-camera notes, monthly projection, storage growth, and overlay availability. Every question is safe to run against sparse data: if the window holds less history than a question needs, it prints a short "not enough data" note instead of guessing (for example, a battery that gained charge is reported as a recharge rather than a negative drain rate).

The pump script only needs the standard library plus websockets — it talks to sqtseries over plain HTTP, so it can run from a different machine, a different venv, or a different language entirely.
