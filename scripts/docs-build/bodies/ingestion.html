Three ways in, one shape

A measurement is four fields of JSON. Send it on a ZeroMQ PUSH socket, an HTTP POST, or through the bundled Python Client — the three are interchangeable and land in the same place.

Words used on this page

Measurement, or point — one value for one metric at one moment. Everything else on this page is machinery around storing those.
Series — one metric with one exact set of tags. The pair is the identity, and it is what a stored row is keyed on.
Topic — the metric name on the wire. Publishing and subscribing both use it.
Frame — one ZeroMQ message. On the ingest path one frame is one measurement.
HWM — high-water mark. The queue limit on a socket; reaching it is how backpressure begins.
Clock skew — how far a client timestamp is from the server clock. A write outside the window is refused.

The message

This is the whole contract. It is the same on every transport, so anything you learn reading it applies everywhere.

{{wire_ingest}}

A minimal message, and a complete one:

// the smallest useful message
{"metric": "cpu.load", "value": 0.42}

// everything, with an explicit time
{
  "metric":    "cpu.load",
  "value":     0.42,
  "tags":       {"host": "web1", "region": "eu-west"},
  "timestamp": 1790786862.857
}
Server-assigned timestamps are forced strictly increasing

When you omit timestamp, the server stamps it — and then walks it forward by at least one nanosecond if it would otherwise collide with the previous one it handed out. The reason is the primary key: a measurement table is keyed on (series_id, timestamp_ns), so two points for the same series at the same nanosecond would violate it and roll back the whole transaction.

The wall clock is coarser than a burst — fifty frames can land inside one clock tick — so without this a burst of untimestamped writes to one metric would lose data. The drift is bounded at 1 ns per assigned point, which is far below any resolution you would ever notice.

Over HTTP

One object, or an array of them. The array is validated in full before anything is stored, so a single bad item rejects the batch rather than leaving a half-written one — which makes a retry safe.

$ curl -X POST http://127.0.0.1:12505/api/v1/write \
    -H "Content-Type: application/json" \
    -d '{"metric":"cpu.load","value":0.42,"tags":{"host":"web1"}}'
{"status":"ok","written":1}

$ curl -X POST http://127.0.0.1:12505/api/v1/write \
    -H "Content-Type: application/json" \
    -d '[{"metric":"cpu.load","value":0.51,"tags":{"host":"web1"}},
         {"metric":"cpu.load","value":0.63,"tags":{"host":"web1"}}]'
{"status":"ok","written":2}

Every accepted measurement is also republished to live subscribers, exactly as the ZeroMQ path does. A write over HTTP is therefore visible on a WebSocket within milliseconds.

What gets refused

All of these are 400, with the reason in detail:

# value must be a number
curl -X POST .../write -d '{"metric":"x","value":"hot"}'
{"detail":"value must be a number"}

# metric must be present and non-empty
curl -X POST .../write -d '{"metric":"","value":1}'
{"detail":"metric must be a non-empty string"}

# tags are string -> string, every pair
curl -X POST .../write -d '{"metric":"x","value":1,"tags":{"n":5}}'
{"detail":"tags must be string->string object"}

# a value must be finite — not NaN, not Infinity
curl -X POST .../write -d '{"metric":"x","value":1e400}'
{"detail":"value must be finite"}

# outside the clock-skew window
curl -X POST .../write -d '{"metric":"x","value":1,"timestamp":1000000000}'
{"detail":"client timestamp skew exceeds 300.0s"}

A boolean is rejected as a value even though Python treats bool as a subclass of int — true is almost never a measurement, and accepting it hides a bug in the caller.

Over ZeroMQ

A PUSH socket, one JSON object per frame, no reply. Connect to the ingest port, which is the one the auto-detector chose — read it from sqtseries ports, not from your config.

$ $PY
>>> import zmq, orjson, time
>>> ctx = zmq.Context()
>>> sock = ctx.socket(zmq.PUSH)
>>> sock.setsockopt(zmq.LINGER, 2000)   # flush on close, do not lose the last point
>>> sock.connect("tcp://127.0.0.1:12500")
>>> for i in range(5):
...     sock.send(orjson.dumps({"metric": "cpu.load", "value": i * 0.1, "tags": {"host": "web1"}}))
...
>>>>>>> sock.close(linger=2000); ctx.term()
Set LINGER before you connect, and keep it non-zero

ZeroMQ drops anything still queued in the send buffer when a socket closes. With the default LINGER = 0, a measurement written microseconds before exit is simply gone — verified: write-then-close delivered 0 of 1. Setting LINGER = 2000 gives the queue two seconds to drain. It must also be set before connect, which is a pyzmq requirement and not a ZeroMQ one.

The bundled Client does both for you.

There is no batch envelope

One frame is one measurement, and that is not an oversight. Throughput comes from many small frames and from committing a burst in one transaction, not from a larger payload. A 10,000-point batch in a single frame would have to be parsed, validated and held whole before anything could be stored, which turns one slow allocation into a stall for every other client.

>>> # faster: many small frames
>>> for point in points:
...     sock.send(orjson.dumps(point))
...

# not faster, and much worse under load: one huge frame
>>> sock.send(orjson.dumps(points))

The persister batches whatever it drained. It draws the batch boundary, not the producer.

From Python

The bundled Client wraps all four sockets. It is the shortest path to a working integration in Python.

$ $PY
>>> from sqtseries import Client
>>> c = Client()

# one point, server-stamped
>>> c.write("cpu.load", 0.42, {"host": "web1"})

# with an explicit time, epoch seconds or ISO-8601
>>> c.write("cpu.load", 0.44, timestamp="2026-09-30T17:00:00Z")

# many points, one frame each — still one loop, still no reply
>>> c.write_many([
...     {"metric": "cpu.load", "value": 0.51, "tags": {"host": "web1"}},
...     {"metric": "mem.used", "value": 3.2,  "tags": {"host": "web1"}},
... ])

>>> c.close()   # flushes the write socket, then closes everything

It is also a context manager, so an exception cannot leak a socket:

>>> with Client() as c:
...     c.write("cpu.load", 0.42)
...     # closed on the way out, LINGER included

Pointing at non-default ports:

>>> c = Client(ports={"write": 12601, "query": 12602,
...                "subscribe": 12603, "admin": 12604})

Tags are dimensions

A tag is a label that splits a metric into a dimension. This is the part of the model worth understanding properly, because getting it wrong is expensive in a way that is not obvious until much later.

The identity of a stored measurement is the pair (metric, tags). Not the metric alone, and not the metric plus an arbitrary identifier:

// three series, not one series with three rows
{"metric": "cpu.load", "value": 0.42, "tags": {"host": "web1"}}
{"metric": "cpu.load", "value": 0.71, "tags": {"host": "web2"}}
{"metric": "cpu.load", "value": 0.33, "tags": {"host": "web3"}}

Querying cpu.load returns all three mixed together, ordered by time. That is usually what you want for a dashboard, and almost never what you want for an alert — which is why knowing this before you have a million rows matters more than it sounds.

You wantDo this
Every host's load in one series query cpu.load with no tag filter
Just web1 query the metric, then filter on the tags in the result — there is no server-side tag filter on the query path
A single flat metric per host use distinct metric names, cpu.load.web1, and no tags
Tags cannot be changed later

There is no update and no delete on the query path, and retention drops whole monthly partitions. So a tag set you write is the tag set that measurement keeps for its whole life. Two consequences worth deciding early:

Do not use a high-cardinality value as a tag. A request ID, a session ID or a full timestamp turns one series per tag value into one series per row, which multiplies the series table and defeats the rollup. Tags are for dimensions with a small number of values — host, region, service, status.

Keep the set of tag keys small and stable. Each distinct set makes its own series. If cpu.load is written once with {host} and once with {host, rack}, that is two series, and a query returns both interleaved.

Values must be strings. The storage layer JSON-encodes the whole set into one column behind a CHECK constraint that rejects anything which is not valid JSON, so a malformed tag set cannot be stored even if validation is bypassed.

Timestamps

Three accepted forms, and one rule that catches people out.

FormExampleNotes
Epoch seconds1790786862.857 A float. Converted to nanoseconds internally.
ISO-8601 with Z2026-09-30T17:00:00Z The clearest option and the one to prefer.
ISO-8601 with an offset2026-09-30T19:00:00+02:00 Converted to UTC.
ISO-8601 with no zone2026-09-30T17:00:00 Read as UTC, not as local time.
ISO-8601, nanoseconds2026-09-30T17:00:00.123456789Z Up to 9 fractional digits. Fewer pad right (.123 is 123 ms); more than 9 truncate.
The nanosecond heuristic

A value whose absolute size exceeds 1e12 is interpreted as nanoseconds rather than seconds. That threshold is what lets an ISO-8601 timestamp survive the JSON round trip as an exact integer: once parsed it becomes something like 1790786862857143900, and on the way back in it is clearly nanoseconds. Epoch seconds never come close to 1e12 — current values are around 1.79e9 — so the two cannot be confused.

The clock-skew guard

With reject_client_timestamp_skew_s at its default of 300, a timestamp more than five minutes from the server clock is refused:

# a 2026-09-11 timestamp written on 2026-09-30
curl -X POST .../write -d '{"metric":"x","value":1,"timestamp":"2026-09-11T14:04:00Z"}'
{"detail":"client timestamp skew exceeds 300.0s"}   # 400

This is deliberate and it protects a real invariant. The hourly rollup only summarises an hour after it has finished — and it waits the skew window before doing so, precisely so that a late write cannot land in an hour already summarised. Without the guard you could write into a closed hour and its value would be invisible to every rollup-served query until the partition was rebuilt.

If your producer's clock cannot be trusted, set reject_client_timestamp_skew_s = 0 and rely on the rollup watermark instead. Note the trade: with the guard off, a write that genuinely lands in a rolled hour is accepted and quietly missing from rollup answers.

When the producer outruns the disk

Ingest is a bounded pipeline, and it stays bounded by pushing back rather than by dropping. Three limits do the work, in this order:

  1. The persister falls behindCommits are slower than arrivals, so batches start queueing. The queue is capped at ingestion.pending_max — 100 batches by default.
  2. The queue is fullThe receive loop stops reading frames. It does not discard them. They sit in the socket, which holds up to ingestion.hwm — 101,000 frames by default, chosen to absorb a producer burst.
  3. The socket is fullPUSH senders block in send(). This is real backpressure, and it propagates to your producer's own write loop.
When a batch genuinely cannot be stored

If the insert fails — a disk error, a corrupt row, a constraint the validation did not anticipate — the whole batch is dropped and its size is added to dropped on the admin socket. The worker survives; one bad batch does not take the service with it.

That is the only way data leaves the pipeline, and it is counted. So dropped and invalid on the admin socket tell you whether anything was lost, without you having to infer it from a gap in the data. A sustained non-zero dropped means the database is rejecting writes; alert on it.

Without a service at all

If your program is a single Python process, you do not need any of this. Open the engine directly — no ports, no service, no serialisation, no other process to supervise.

$ $PY
>>> from sqtseries.engine import StorageEngine, create_sqlite_engine
>>> from sqtseries import TimeSeriesDB
>>> import time

>>> engine = create_sqlite_engine("/tmp/embedded.sqlite")
>>> db = TimeSeriesDB(StorageEngine(engine))

>>> db.insert("cpu.load", 0.42, {"host": "web1"})
>>>>>>> 1
>>> db.query("cpu.load")
[(1790786862857143900, 0.42)]

>>> db.aggregate("cpu.load")
{'avg': 0.42}

>>> db.close(); engine.dispose()

Same schema, same query code, same rollup. The difference is only that query returns nanoseconds here rather than seconds, because there is no gateway doing the conversion. The full embedded API is on API Reference.

Use both HTTP and ZeroMQ against the same service if you like. They converge on the same tables, the same rollup, and the same live stream — and the admin counters merge them, so there is no way to tell afterwards which transport a point arrived on.
