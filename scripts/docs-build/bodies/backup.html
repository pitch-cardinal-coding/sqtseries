What to back up, and how

The whole database is one file, so backing it up feels trivial. It is nearly trivial — but the obvious way of doing it, copying the file, quietly loses the most recent writes.

Words used on this page

WAL — SQLite's write-ahead log. A second file holding committed pages not yet merged into the main database.
Shared-memory file — the third file WAL mode creates, coordinating readers against the WAL.
Snapshot — a VACUUM INTO result: one complete, consistent, self-contained file.
Partition — one monthly table, measurements_YYYY_MM.
Retention — the policy that drops whole partitions past their time to live, rollup rows included.
Vacuum — rewriting the file to reclaim free pages. Not a backup.

Why you cannot just copy the file

In WAL mode a live database is three files: the main database, the write-ahead log, and the shared-memory file. Only the main file is what most people think of as "the database".

Taking a snapshot

From the command line

One command. It is safe against a running service.

$ sqtseries backup
backup written to /home/iam/.sqtseries/backups/sqtseries-20260930-172525.db

# against a different database, with no config file
$ sqtseries --db /path/to/other.sqlite backup

Over the admin socket

Same operation, no client library, usable from any language over ZeroMQ:

$ $PY
>>> from sqtseries import Client
>>> c = Client()
>>> c.admin("backup")
{'status': 'ok', 'path': '/home/iam/.sqtseries/backups/sqtseries-20260930-173012.db'}
The admin command pauses ingest while it runs

VACUUM INTO needs to read the database, and the admin handler runs on the service's single SQLite writer. The admin socket has no handler timeout — a large snapshot legitimately takes a while — but ingest is paused for the duration.

For anything large, stop the service and use the offline sqtseries backup instead. The command-line path is also the one to put in a cron job.

Automatically

On by default. The service takes one snapshot at first start, then one every backup.interval — every 24 hours out of the box.

# config.toml
[backup]
enabled  = true
interval = "24h"
path     = "/mnt/backups/sqtseries/"   # any writable path

A pass that finds a snapshot younger than the interval counts the run and writes nothing — so restarting the service repeatedly cannot produce a stack of copies in the same second. Watch backups_created and backup_runs on the admin socket: if runs climb but creations do not, a snapshot is already fresh.

What the files are called

sqtseries-YYYYmmdd-HHMMSS.db under backup.path. A name that already exists is kept, never overwritten — a same-second retry after a restart is skipped rather than raising. Sorted by name, the newest is last, which is how backup_latest finds it.

Restoring

Four steps. The fourth is the one people skip, and skipping it is how a backup turns out to have been useless six months later when it was needed.

  1. Stop the serviceLeave the original database alone — you want it still there if the snapshot turns out to be wrong. Do not delete or move it until the restore has been verified.
  2. Put the snapshot where the config expects itKeep the old file under a different name rather than overwriting it, so the two can be compared. Remember the -wal and -shm files belong to the old database and must not be left beside the new one.
  3. Start the serviceIt recovers any uncommitted WAL frames, runs the schema migration and the integrity check, and creates the current month's partition if needed.
  4. Verify — do not skip thisCheck the database is sound and that the data is actually there. An unrestored backup is a guess.
# 1. stop
$ sqtseries stop
Sent SIGTERM to pid 178445

# 2. move the old one aside, put the snapshot in place
$ cd ~/.sqtseries/data
$ mv db.sqlite db.sqlite.before-restore
$ rm -f db.sqlite-wal db.sqlite-shm     # belongs to the OLD file
$ cp ~/.sqtseries/backups/sqtseries-20260930-172525.db db.sqlite

# 3. start
$ sqtseries run

# 4. verify — from another terminal
$ sqtseries health
ok
$ sqtseries stats
metrics: 3
series:  12

# and read something you know was stored before the snapshot
$ curl -s "http://127.0.0.1:12505/api/v1/aggregate?metric=cpu.load&funcs=avg,min,max,count"
{"status":"ok","aggregations":{"avg":0.54,"min":0.42,"max":0.77,"count":3.0}}
Restore into a scratch path first

Before you touch the live database, prove the snapshot opens and answers. This needs no service and no risk:

$ sqtseries --db /tmp/restore-test.sqlite health
ok
$ sqtseries --db /tmp/restore-test.sqlite stats
metrics: 3
series:  12

# or read it with sqlite3 directly
$ sqlite3 /tmp/restore-test.sqlite "PRAGMA integrity_check; SELECT COUNT(*) FROM series;"
ok
12

Copy the snapshot to the scratch path first — --db will create and migrate a fresh empty file if the path does not exist, which would "verify" nothing at all.

The restored database answers historical queries identically

A snapshot contains the schema, the series table, every partition inside the retention window, and the hourly rollup rows for those partitions. So a restored service answers questions about last month exactly as before, and does not have to wait for the rollup to catch up over the next rollup.interval.

The current partial hour is the exception: the snapshot was taken at a moment, and writes after it are of course not in it. That is the expected cost of a point-in-time backup, and it is why the interval is a choice.

Vacuum is a different job

Reclaiming disk space is not the same activity as protecting data, and the two are easy to confuse.

BackupVacuum
What it doescopies the database elsewhere rewrites the database in place
Protects datayesno
Reclaims spacenoyes
Needs the service stoppedno yes, for anything large
Blocks ingestnot meaningfully yes, for its whole duration
 
# reclaim space: stop the service first for anything big
$ sqtseries stop
$ sqtseries vacuum
VACUUM complete
$ sqtseries run

Over the admin socket there is a vacuum command too, and it will refuse politely if the database is in use:

>>> c.admin("vacuum")
{'status': 'error', 'error': {'code': 'VACUUM_BUSY',
 'message': 'vacuum failed while running; stop the service and use `sqtseries vacuum`: …'}}

You rarely need to. SQLite reuses free pages internally, so the file only grows when there is genuinely more data. A file that keeps growing under retention.enabled = true is worth investigating — it usually means partitions are not being dropped.

How much to keep

Retention already bounds the database, so the backup question is smaller than it looks. Choose a retention window that matches what you actually need, and a backup interval that matches how much you would have to re-enter.

GoalSettingWhy
Bound the file sizeretention.default_ttl Partitions past the TTL are dropped whole, rollup rows included, so deleted data leaves no aggregate trace.
Bound re-entry workbackup.interval Worst-case loss is one interval, plus the partial hour at the snapshot moment.
Keep history cheaprollup.enabled On, so wide queries read summary rows instead of scanning raw points.
 
# a year of history, snapshotted daily
[retention]
default_ttl = "365d"
check_interval = "1h"

[backup]
enabled  = true
interval = "24h"
path     = "/mnt/backups/sqtseries/"

365d, not 12m — m means minutes. See Configuration for both duration syntaxes.

A snapshot is a full database, so they add up

Each one is the whole thing, not an increment. Twenty daily snapshots of a 2 GB database is 40 GB. If that matters, keep fewer, keep them compressed, or take snapshots less often and accept a larger worst-case loss. This is the trade the VACUUM INTO approach makes deliberately: a snapshot you can restore without a second tool is worth more than one that is a third of the size.

Checking on it

Two counters, on the admin socket or the dashboard:

>>> st = c.admin("stats")
>>> st["backup_runs"], st["backups_created"], st["last_backup"]
(3, 3, '/home/iam/.sqtseries/backups/sqtseries-20260930-172525.db')

backup_runs counts passes; backups_created counts files actually written. Equal numbers mean every pass wrote something. Runs climbing while creations stay flat means a recent snapshot was found and kept — normal, and the reason a restart loop cannot fill the disk.

# the files on disk
$ ls -laht ~/.sqtseries/backups/ | head
# and the newest one
$ ls -t ~/.sqtseries/backups/sqtseries-*.db | head -1
