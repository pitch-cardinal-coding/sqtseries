Everything the service exposes

Seven REST routes, three WebSockets, the admin socket, the ZeroMQ wire format, the embedded Python API and the CLI — with the exact parameter names, the accepted ranges, and the error code each failure returns.

Words used on this page

Status envelope — the {"status":"ok", …} or {"status":"error","error":{…}} wrapper every reply uses.
Error code — a stable machine-readable string. Match on this, never on the message.
Frame — one ZeroMQ message. Ingest and query are one part; the stream and stats sockets are two ([topic, json]).
Registry — the service's record of connections and subscriptions.
Snapshot — full state, once, on connect.
Tick — counters only, on a timer.
OpenAPI — /openapi.json, generated from the route definitions.

Two different error codes for a bad parameter

It depends on who rejects it. A value the route signature declares — limit out of range, order not matching its pattern — is caught by the framework before the handler runs and comes back as 422 with a structured detail array. A value the handler checks — an unknown aggregation, a limit of 0 on the ZMQ path, an unparseable timestamp — comes back as 400 with a plain string in detail.

# 422 — rejected by the route signature
curl -s "…/api/v1/read?metric=cpu.load&limit=0"
{"detail":[{"type":"greater_than_equal","loc":["query","limit"],
  "msg":"Input should be greater than or equal to 1","ctx":{"ge":1}}]}

# 400 — rejected by the handler
curl -s "…/api/v1/read?metric=cpu.load&aggregation=bogus"
{"detail":"unsupported aggregation: bogus"}

Response shapes

# GET /api/v1/read
{"status":"ok", "data":[{"timestamp":1790793328.2546144, "value":31.0}, …]}
#   timestamp is EPOCH SECONDS even though it is stored as nanoseconds

# GET /api/v1/aggregate
{"status":"ok", "aggregations":{"avg":62.27, "p99":99.85}}
#   a function with no value is null, not 0

# POST /api/v1/write
{"status":"ok", "written":3}

# GET /api/v1/health — never fails, so a load balancer can poll it
{"status":"ok", "version":"0.1.0"}
{"status":"degraded", "version":"0.1.0"}

# GET /api/v1/stats
{"status":"ok", "metrics":2, "series":12}

# GET /api/v1/subscribers
{"status":"ok", "zmq_subscribers":0, "topics":[
  {"topic":"temp.outside", "subscribers":0, "first_seen":null, "total":null}]}

A stored metric nobody subscribes to still appears in topics, with subscribers: 0. That is deliberate: a zero row and a missing row are different facts when you are working out whether a producer stopped.

The write body is validated as a unit

Send a JSON array and the whole array is checked before any of it is stored. One bad item rejects the batch with 400 and nothing is written, so a retry is safe — there is no half-applied batch to reconcile.

curl -X POST http://127.0.0.1:12505/api/v1/write \
  -H "Content-Type: application/json" \
  -d '[{"metric":"cpu.load","value":0.42,"tags":{"host":"web1"}}]'
# the Content-Type header is required — see Client Libraries

What each one looks like

# ZMQ — one-part reply, status envelope either way
{"status":"error", "error":{"code":"INVALID_QUERY", "message":"unsupported aggregation: bogus"}}
{"status":"error", "error":{"code":"INVALID_QUERY", "message":"limit must be a positive integer"}}
{"status":"error", "error":{"code":"INVALID_QUERY", "message":"either metric or series_ids required"}}
{"status":"error", "error":{"code":"INVALID_QUERY", "message":"timestamp not ISO-8601: 'not-a-time'"}}
{"status":"error", "error":{"code":"MAX_ROWS_EXCEEDED", "message":"query would materialize more than max_rows=10000 raw rows; …"}}
{"status":"error", "error":{"code":"INVALID_REQUEST", "message":"invalid JSON: unexpected character: line 1 column 2 (char 1)"}}
{"status":"error", "error":{"code":"INVALID_REQUEST", "message":"unknown admin command: nope"}}

# HTTP — detail is a string for handler errors, an array for schema errors
{"detail":"metric must be a non-empty string"}                    # 400
{"detail":"tags must be string->string object"}                 # 400
{"detail":"client timestamp skew exceeds 300.0s"}                   # 400
{"detail":"query would materialize more than max_rows=10000 raw rows; …"} # 413
{"detail":"query exceeded 30.0s"}                                  # 504
{"detail":[{"type":"string_pattern_mismatch", …}]}                # 422
{"status":"error","error":{"code":"RATE_LIMITED",…}}  # 429
413 and 504 mean what they say here

413 is not "your payload was too large" — the request was valid and it is the result that exceeds the bounded-work policy. 504 is the query timeout, and the query keeps running in the background; its result is discarded.

Both are the bounded-queue doctrine applied to reads: the cap exists so one query cannot make the service's memory grow with the size of the database, and it is better to refuse loudly than to answer with a plausible subset.

The admin socket

Port 12504, one request and one reply. {"cmd": "…"} in, a status envelope out. This is the surface to use from a monitoring script: it needs no HTTP client and no WebSocket, and it answers operational questions the REST API does not.

The bundled Client raises ClientError with the message; over raw ZMQ you get the envelope and check status yourself.

The WebSocket protocols

/ws/subscribe?metric=…

Live measurements for one topic pattern. Push only: inbound frames are consumed and ignored, but consuming them is what makes a disconnect surface at once instead of at the next send.

{"metric": "cpu.load", "tags": {"host": "web1"}, "value": 0.42}
{"type": "ping"}   # after 30 s of silence — the stream is alive, there is just no data

Pattern matching is boundary aware: * takes everything, cpu. is a plain prefix, and cpu matches cpu.load but not cpu10. Full rules on Streaming.

/ws/connections

One snapshot, then a frame per change. Event-driven, with no polling.

 "connections": [{"id": "a1b2c3d4e5f6", "kind": "ws", "peer": "10.0.0.7:52344", "topic": "cpu."}],
 "topics": [{"topic": "cpu.load", "subscribers": 1, "first_seen": 1790786862.85}]}

{"type": "conn", "id": "a1b2c3d4e5f6", "kind": "ws", "peer": "10.0.0.7:52344",
 "topic": "cpu.", "connected": true, "connected_at": 1790786862.85, "ttl": 60}

{"type": "conn", "id": "a1b2c3d4e5f6", "connected": false,

The units difference, one last time

Over ZMQ the query message takes epoch nanoseconds as an integer. Over HTTP the same field takes epoch seconds. Both return seconds. Getting it wrong yields an empty result with no error, so it is worth stating plainly even though it is the third time on these pages.

The embedded Python API

No sockets, no ports, no service. The same query code the service itself uses, with a store and a facade constructed in-process.

from sqtseries.engine import StorageEngine, create_sqlite_engine, run_migrations
from sqtseries import TimeSeriesDB
import time

engine = create_sqlite_engine("/tmp/embedded.sqlite")
run_migrations(engine)                       # create the schema if new
db = TimeSeriesDB(StorageEngine(engine), max_rows=10000)
MethodArgumentsReturns
insertmetric, value, tags=None, timestamp_ns=None rows inserted
query metric=None, series_ids=None, start=None, end=None, *, aggregation=None, interval=None, limit=None, order="asc", fill_gaps_ns=None [(timestamp_ns, value), …]
query_streammetric, start=None, end=None, *, order="asc" an iterator — bounded memory over any window
aggregatemetric, start=None, end=None, *, funcs=None {func: value}
downsamplemetric, start=None, end=None, *, interval="5m", aggregation="avg" [(timestamp_ns, value), …]

start and end accept nanoseconds or an ISO-8601 string. Returns are nanoseconds — there is no gateway here to convert them.

Two things only the embedded API can do

  • query_stream — yields rows without ever holding the whole result in memory, so a month-long scan costs one row of memory.
  • fill_gaps_ns — inserts an interpolated midpoint across gaps no larger than the given size. It is not on the wire because a row you interpolated is not a row anybody measured.

To query by series identity rather than by metric name, resolve the ids first — useful when a metric has many tag sets and you want one of them:

>>> store = StorageEngine(engine)
>>> sids = store.series_ids_for_metric("cpu.load")
>>> db.query(series_ids=[sids[0]], limit=5)

The CLI

Eleven commands and two global flags. The full table, with what each needs, is on Configuration; this is the shape of it.

$ sqtseries --config PATH --db PATH COMMAND

# lifecycle
sqtseries run                 # foreground; prints the links
sqtseries stop                # SIGTERM, then wait for exit

# inspection
sqtseries status              # pid, version, real ports, links
sqtseries ports               # the ports actually bound
sqtseries health              # quick_check; exit 0 or 1
sqtseries stats               # metric and series counts

# maintenance
sqtseries backup              # VACUUM INTO snapshot
sqtseries optimize            # PRAGMA optimize
sqtseries vacuum              # full VACUUM; stop the service first

# service unit
sqtseries install             # add --system for a root unit
sqtseries uninstall
Global flags come before the subcommand

They belong to the command group, not to a command, so sqtseries --config c.toml run is correct and sqtseries run --config c.toml is an error.

Response headers

Set on every HTTP response, so a page served by the gateway inherits them:

HeaderValueWhy
X-Request-IDyour value, or 12 hex characters correlate a client report with a log line
X-Frame-OptionsDENY the API cannot be framed
X-Content-Type-Optionsnosniff no content-type guessing
Referrer-Policystrict-origin-when-cross-origin no referrer leakage to third parties
Permissions-Policy geolocation, microphone, camera, payment, usb all () the API needs none of them
Content-Security-Policy default-src 'self'; img-src 'self' data: no third-party origins at all

The /docs path is the one exception: it adds style-src 'self' 'unsafe-inline' so the single-file pages, whose stylesheet is inlined, render when copied elsewhere. script-src is not relaxed anywhere, and the API keeps the strict default.
