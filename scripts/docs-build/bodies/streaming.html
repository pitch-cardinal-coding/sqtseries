Watching values arrive

Three live paths carry measurements as they land: a ZeroMQ SUB socket, the /ws/subscribe WebSocket, and the bundled Python Client. A fourth carries connection events instead of data, which is how you answer "who is watching what" without polling.

Words used on this page

Topic — the metric name on the wire. Publishing and subscribing both use it, and it is what a subscription pattern is matched against.
Frame — on the stream socket, two parts: the topic, then the JSON payload.
XPUB — a publish socket that also receives subscribe and unsubscribe events. This is why the counts are exact.
Keepalive — a frame sent when the stream is idle, so a client can tell "nothing happening" from "connection dead".
Fan-out hub — the in-process path that hands each frame to WebSocket subscribers, with a bounded queue per subscriber.
Drop — a frame deliberately not delivered to one slow subscriber, and counted. Not the same as an error.

The guarantee that matters

You will never see a point that was not stored

Publishing happens strictly after the commit succeeds. If the insert fails, nothing is published for that batch. So the live stream and the stored data never disagree in the direction that matters — you cannot be alerted on a value that turns out not to have been recorded.

The ordering is deliberate and it is the opposite of the obvious choice. It would be simpler to publish as soon as a frame parses, before the commit. That would let a subscriber act on a point which a moment later failed to persist.

Two things reach a subscriber, then. The measurement itself, and — after 30 seconds of silence — a keepalive:

// a measurement, as one WebSocket text frame
{"metric": "cpu.load", "tags": {"host": "web1"}, "value": 0.42}

// the keepalive, after 30 s with nothing to send
{"type": "ping"}

Over ZeroMQ SUB

Connect to port 12503, subscribe with a topic pattern, and read two-part frames. The topic is frame 0 and the JSON is frame 1 — the split is what makes prefix filtering happen in the socket rather than in your loop.

$ $PY
>>> import zmq, orjson
>>> ctx = zmq.Context()
>>> sub = ctx.socket(zmq.SUB)
>>> sub.setsockopt(zmq.SUBSCRIBE, b"cpu.")   # empty bytes = every topic
>>> sub.connect("tcp://127.0.0.1:12503")
>>> while True:
...     topic, payload = sub.recv_multipart()
...     print(topic.decode(), orjson.loads(payload))
...
cpu.load {'metric': 'cpu.load', 'tags': {'host': 'web1'}, 'value': 0.42}
cpu.load {'metric': 'cpu.load', 'tags': {'host': 'web1'}, 'value': 0.51}

The bundled Client does the same thing with the two details that usually go wrong handled for you:

>>> for payload in c.subscribe("cpu.", timeout=0.5):
...     if payload is None:
...         # idle, or the client is closing — not an error
...         # this is the heartbeat: your loop never blocks forever
...         continue
...     print(payload)
Why the iterator yields None

It polls with a timeout instead of blocking in recv(). That gives you two things: a periodic wake-up so a shutdown flag can be honoured, and a clean exit when close() is called from another thread — a recv() interrupted by context teardown raises, and turning that into a plain return is the difference between a cooperative stop and a crash in someone else's teardown path.

Every resync_interval_s (30 s by default) the client compares the server's uptime against the last one it saw. A lower value means the server restarted, so it rebuilds the socket and re-subscribes. ZeroMQ's own reconnect does not reliably re-deliver subscriptions after a server bounce — a session can re-handshake and still stay invisible indefinitely — so without this a subscriber can go quiet after a restart and never notice.

Over a WebSocket

Same data, same topics, no library. One query parameter selects the topic.

# every topic
ws = new WebSocket("ws://127.0.0.1:12505/ws/subscribe?metric=*")

# one topic
ws = new WebSocket("ws://127.0.0.1:12505/ws/subscribe?metric=cpu.load")

# a prefix
ws = new WebSocket("ws://127.0.0.1:12505/ws/subscribe?metric=cpu.")

ws.onmessage = e => console.log(e.data)
// in Python, with websockets (no extra dependency)
>>> import asyncio, json, websockets

>>> async def watch():
...     uri = "ws://127.0.0.1:12505/ws/subscribe?metric=cpu."
...     async with websockets.connect(uri) as ws:
...         async for frame in ws:
...             msg = json.loads(frame)
...             if msg.get("type") == "ping":
...                 # idle keepalive; the stream is alive
...                 continue
...             print(msg)

>>> asyncio.run(watch())

The subscribe socket is push only. Inbound frames are consumed and ignored, but they still reset the activity clock — which is deliberate, because consuming them is what makes a disconnect surface immediately instead of up to 30 seconds later on the next send.

How a topic pattern is matched

Three rules, and the third one is the one that surprises people. Matching is boundary-aware, so a filter cannot accidentally fan one topic out to its neighbours.

PatternMatchesRule
*everythingthe wildcard
cpu.cpu.load, cpu.temptrailing dot = plain prefix, kept for compatibility
cpucpu, cpu.load the topic itself and its dot-delimited children
cpunot cpu10, cpuspeedno match across a boundary, so a shared textual prefix is not enough
Why the boundary check exists

Plain str.startswith() matching meant that a subscription of stress.m1 also received stress.m10, stress.m11, stress.m100 and the rest. Under a stress test that is ten machines' worth of traffic delivered to one client that asked for one — measured at roughly 7× delivery amplification.

The boundary rule fixes it: a dot-less pattern matches only the exact topic and names that continue with a dot. If you genuinely want a shared textual prefix, say so with the trailing dot.

A slow subscriber costs only itself

Every WebSocket subscriber gets its own queue, bounded in bytes rather than in message count. Bytes, because what costs memory is payload size, not the number of frames.

One exception, on purpose

A single frame larger than the whole byte budget is delivered anyway rather than being permanently undeliverable. A client on an empty queue that cannot fit one frame would otherwise never receive anything at all, and the queue would stay empty forever. The bound is on backlog, not on message size.

How to tell a drop from a gap in your data

A dropped live frame was still stored. The live stream is lossy for slow subscribers by design; the database is not lossy at all. So a value missing from a live feed but present in a query is expected behaviour, and the fix is to read history rather than to raise the budget.

Watch fanout_dropped on the admin socket. A non-zero value means at least one subscriber cannot keep up. If it is your client, make it read faster or subscribe to fewer topics.

Watching the watchers

Two endpoints report who is connected, and both push — neither polls.

/ws/connections

One snapshot on connect, then a frame per change. Three message types:

// 1. on connect — everything, once
{"type": "snapshot",
 "ws_connections": 2,
 "zmq_subscribers": 1,
 "connections": [
   {"id": "a1b2c3d4e5f6", "kind": "ws",
    "peer": "10.0.0.7:52344", "topic": "cpu."}
 ],
 "topics": [
   {"topic": "cpu.load", "subscribers": 1, "first_seen": 1790786862.85}
 ]}

// 2. a client arrived or left
{"type": "conn", "id": "a1b2c3d4e5f6", "kind": "ws",
 "peer": "10.0.0.7:52344", "topic": "cpu.",
 "connected": true, "connected_at": 1790786862.85, "ttl": 60}

{"type": "conn", "id": "a1b2c3d4e5f6", "connected": false,
 "connected_at": 1790786862.85, "left_at": 1790787162.90}

// 3. a ZeroMQ subscriber joined or left a topic
{"type": "sub", "kind": "zmq", "topic": "cpu.load",
 "subscribers": 2, "arrived_at": 1790786900.1, "ttl": 30}

{"type": "sub", "topic": "cpu.load", "subscribers": 1,
 "left_at": 1790786960.2, "first_seen": 1790786862.85}

A leave event carries both times, so a consumer can show how long the connection lasted without keeping its own record.

/ws/dashboard

The admin dashboard feed: a full snapshot, then live events, then a counter tick every second. The tick deliberately omits the two list-shaped keys — sending the whole connection list every second would be waste when it already arrives as events.

{"type": "snapshot", "status": "ok", "server_time": 1790786862.85,
 "uptime_s": 412.7, "ingested": 40218, "persisted": 40218,
 "dropped": 0, "invalid": 0, "queries": 88,
 "series": 3, "metrics": 2, "db_bytes": 86016,
 "partitions": 1, "rollup_watermark": 1790784000000000000,
 "ports": {"ingest": 12500, "query": 12502, "streaming": 12503,
              "admin": 12504, "http": 12505, "stats": 12506},
 "connections": [ … ], "topics": [ … ]}

// one second later
{"type": "tick", "uptime_s": 413.7, "ingested": 40318,
 "persisted": 40318, "queries": 91, "db_bytes": 88128, …}

rollup_watermark is the next hour the rollup will process, in nanoseconds. It sitting still while ingested climbs is normal — the current hour is never rolled.

The stats socket

Port 12506 publishes the same events as a plain ZeroMQ PUB socket, for anything that is not a browser. Subscribe with an empty prefix for everything, or with a topic name to take one kind.

>>> import zmq, orjson
>>> sub = ctx.socket(zmq.SUB)
>>> sub.setsockopt(zmq.SUBSCRIBE, b"")   # conn, sub and report
>>> sub.setsockopt(zmq.SUBSCRIBE, b"conn")
>>> sub.connect("tcp://127.0.0.1:12506")
>>> while True:
...     topic, payload = sub.recv_multipart()
...     print(topic.decode(), orjson.loads(payload))
...
conn {'kind': 'ws', 'id': 'a1b2c3d4e5f6', 'connected': True, …}
sub  {'kind': 'zmq', 'topic': 'cpu.load', 'subscribers': 1, …}
report {'uptime_s': 420.1, 'ws_connections': 2,
        'zmq_subscribers': 1, 'active_topics': 1}
Why the counts are exact

The stream socket is an XPUB, not a PUB, with XPUB_VERBOSER on. That combination means the service receives an event for every join and leave, rather than only when a topic is first heard of. The default only reports the first subscriber to a topic, which would mean two clients on one topic counted as one — verified on libzmq 4.3.5.

So zmq_subscribers is a real count taken from the wire, not an estimate. There is no polling anywhere in this path.

Set stats.enabled = false and port 12506 is never bound, if you do not want the surface at all.

Asking after the fact

Both endpoints have an HTTP equivalent, which is what you want from a script or a monitoring check rather than a live subscription.

$ curl -s http://127.0.0.1:12505/api/v1/connections
{"status":"ok","data":[]}

$ curl -s http://127.0.0.1:12505/api/v1/subscribers
{"status":"ok","zmq_subscribers":0,
 "topics":[{"topic":"temp.outside","subscribers":0,"first_seen":null,"total":null}]}

The subscribers list is the union of two sources: every topic the registry has ever seen, and every metric currently stored. A stored metric nobody is watching appears with subscribers: 0, which is how you tell "quiet" apart from "unknown".

The same two are available over the admin socket, which needs no HTTP client:

>>> c.admin("connections")
{'status': 'ok', 'data': []}

>>> c.admin("subscribers")
{'status': 'ok', 'zmq_subscribers': 0, 'topics': [ … ]}

# which of these ids are still connected?
>>> c.admin("conncheck", ids=["a1b2c3d4e5f6", "deadbeef0000"])
{'status': 'ok', 'present': ['a1b2c3d4e5f6']}

conncheck is the one to use in a health check: it is a cheap membership test against ids you recorded earlier, and it does not hand back the whole connection list to parse.
