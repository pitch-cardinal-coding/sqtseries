Install it as a service

The service is meant to run for years unattended. One command writes a hardened systemd unit, and this page explains every line of it.

Words used on this page

Unit — the systemd service file, sqtseries.service.
User unit — under ~/.config/systemd/user/, no root, stops when you log out unless lingering is on.
System unit — under /etc/systemd/system/, runs at boot for good.
Hardening — systemd directives that restrict what the process may touch.
Restart policy — what systemd does when the process exits.
Journal — the log, read with journalctl.
Lingering — loginctl enable-linger, which keeps a user unit alive with nobody logged in.

The command

Install it with the same configuration you actually want. The unit embeds the flags it was installed with, so a service that serves custom ports does not come back on the defaults after a reboot.

# a user unit — no root needed
$ sqtseries --config ~/sqtseries.toml install
systemd unit installed

# a system unit — runs at boot, needs root
$ sudo sqtseries --config /etc/sqtseries/config.toml install --system
systemd unit installed

install writes the file, runs daemon-reload, and enables and starts the unit. There is no separate enable step.

Install with your config, every time

The unit's ExecStart is built from the arguments you pass to install. Install without --config and the service will boot with whatever ~/.sqtseries/ happens to say at that moment, which is not the same thing as the ports you tested.

It also embeds the resolved database path as SQT_SERIES_DATABASE__PATH. Installing a system unit as root against a default path would put the database under /root, so the installer detects the human who ran sudo and re-anchors the path into their home — including the case where ~ had already expanded to /root before the installer ever saw it.

The most common surprise with a user unit is that it stops when you log out. Enable lingering once:

$ loginctl enable-linger $USER

The generated unit

This is the real output, with a real config. Yours will differ in the paths and the Python interpreter.

[Unit]
Description=sqtseries time-series database
After=network.target
StartLimitIntervalSec=60
StartLimitBurst=3

[Service]
Type=simple
ExecStart=/home/iam/devcode/.env/sqtseries/bin/python3 -m sqtseries --config /home/iam/sqtseries.toml run
Restart=on-failure
RestartSec=5
StandardOutput=journal
StandardError=journal
SyslogIdentifier=sqtseries
# Security hardening
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=read-only
ReadWritePaths=/home/iam/.sqtseries/data /home/iam/.sqtseries/backups

# Environment
Environment=LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2
Environment=SQT_SERIES_DATABASE__PATH=/home/iam/.sqtseries/data/db.sqlite
Environment=SQT_SERIES_LOGGING__LEVEL=INFO

[Install]
WantedBy=default.target

Every line, and why it is there

DirectiveWhat it does
After=network.target Waits for networking. The ZMQ and HTTP ports are loopback and HTTP, so this is about ordering, not about a remote peer.
StartLimitIntervalSec=60 With the next line: at most three starts in any 60-second window.
StartLimitBurst=3 A service that crashes on boot four times in a minute is then left stopped rather than restarted forever. Without this a bad config produces an infinite loop that fills the journal.
Type=simple The process is the service; systemd does not fork or track a pid file.
ExecStart=… Built from your install arguments, with the paths shell-quoted.
Restart=on-failure Restart on a non-zero exit or a signal, but not on a clean exit. A deliberate sqtseries stop stays stopped.
RestartSec=5 Five seconds between attempts, so a crash does not spin.
StandardOutput/Error=journal Logs go to the journal, where journalctl can find them. SyslogIdentifier is what you grep on.
User=… System units only, and only when the installer resolved a non-root installing user. Without it a system unit runs as root.
NoNewPrivileges=true Nothing the process does can gain privilege — no setuid binary, no child process escalating. A large part of why a parser bug in a dependency is survivable.
ProtectSystem=strict The entire filesystem is read-only to the process, including /usr and /etc. It cannot rewrite its own dependencies or a system config file.
ProtectHome=read-only Everything under every home directory is read-only — so the process can read the database but cannot damage anything else in your home. System units instead set this to false, because the data directory lives there and has to be writable.
ReadWritePaths=… The only exceptions, and there are exactly two: the data directory and the backup directory. Every other path stays read-only.
Environment=LD_PRELOAD=… jemalloc, but only if it is present. The service is correct without it; preloading just trims memory retained under sustained load. A missing library is not an error.
Environment=SQT_SERIES_DATABASE__PATH The resolved path, so the unit and the command line agree even if the config file moves.
ReadWritePaths is the whole point

ProtectSystem=strict plus ProtectHome=read-only would leave the service unable to write its database at all, because the default path is under ~. ReadWritePaths re-opens exactly the two directories it needs and nothing else. The process can read the whole system and write almost none of it.

$ systemd-analyze security sqtseries.service

Running it

# user unit
$ systemctl --user status sqtseries
# system unit
$ sudo systemctl status sqtseries

# the log
$ journalctl --user -u sqtseries -f
#   follow it live
$ journalctl -u sqtseries -n 100 --no-pager
#   since the last boot
$ journalctl -u sqtseries -b --no-pager

# restart, and stop
$ systemctl --user restart sqtseries
$ systemctl --user stop sqtseries

Note that systemctl stop and sqtseries stop are not the same thing. The first asks systemd to stop the unit, which sends SIGTERM and gives the process its normal shutdown. The second sends SIGTERM and waits for the port to actually be free. Either is fine; the second is what you want inside a script that is about to rebind the ports.

Proving the restart policy works

An untested restart policy is a hope, not a plan. This takes thirty seconds.

# 1. find the pid
$ systemctl --user show sqtseries --property MainPID
MainPID=1234

# 2. kill it uncleanly — no chance to flush anything
$ kill -9 1234

# 3. wait, and watch it come back with a different pid
$ sleep 8
$ systemctl --user show sqtseries --property MainPID
MainPID=1290

# 4. and the data survived
$ sqtseries health
ok
$ sqtseries stats
metrics: 3
series:  12
Why a SIGKILL does not lose data

Because every commit goes through SQLite's write-ahead log first. A commit is durable when it is written to the WAL, not when it reaches the main file — so kill -9 can lose at most a commit that had not been written, and the next start replays the WAL.

What a hard kill can cost is a frame that was accepted into the socket queue but not yet persisted, since the shutdown drain that would have flushed it never ran. That is inherent to a hard kill; the graceful path is what avoids it, and the difference is why sqtseries stop exists.

Shutting down cleanly

SIGTERM starts an ordered shutdown, and the order is the point.

  1. Stop the background tasksRollup, retention, maintenance and backup are cancelled so none of them starts new work.
  2. Drain the ingest socketFrames already accepted are swept and queued. This happens before the socket closes, because closing discards whatever libzmq still holds.
  3. Flush the persisterEvery queued batch is committed, behind a bounded 60-second budget so a wedged disk cannot hang the stop forever.
  4. Stop the brokers and the gatewayIn-flight query replies are allowed to drain, then the HTTP server is given five seconds to finish its connections.
  5. Checkpoint the WALPRAGMA optimize and a TRUNCATE checkpoint, so the next start is fast and the file is compact.
  6. Remove the runtime fileThe last step. sqtseries status uses its absence, so a restart script that waits for it knows the process is really gone — not merely answering to signal 0 as a not-yet-reaped zombie does.

Under systemd, SIGTERM arrives the same way, so a restart never discards a frame that was already accepted. A hard kill skips all of it, which is the difference the test above demonstrates.

Uninstalling

# user unit
$ sqtseries uninstall
systemd unit removed

# system unit
$ sudo sqtseries uninstall --system
systemd unit removed

This stops the unit and removes the file. It does not touch your database or your backups — they are yours, and deleting a database because someone removed a service file would be a nasty surprise. Delete ~/.sqtseries/ yourself when you mean it.
