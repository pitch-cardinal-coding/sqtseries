Runnable, and run

Eighteen runnable example scripts in the repository, each one executed against a live service by the test suite. A sample that stops working fails a test, so nothing here can quietly rot.

Before you run the question examples

The two question catalogues seed 6 hours to 8 days of history. The default reject_client_timestamp_skew_s is 300, so a service with default settings refuses every one of those writes.

They now fail loudly rather than printing "no data" and exiting 0, so if you see this you know exactly what happened:

seed did not land for cpu.load, temp.celsius, latency.web, visitors.web (counts={…: 0.0}).
This service rejects historical writes: set ingestion.reject_client_timestamp_skew_s = 0
to seed demo history.

To run them, either start the service with that setting, or use run_all_examples.py, which does it for you. The guard is correct behaviour — it stops a client's clock drift from writing into an hour that has already been summarised. The examples simply need to write history on purpose.

What PASS means, and what it does not

The runner checks the exit code of each script. A script that printed nonsense and exited 0 would pass — which is exactly how the question examples managed to report a pass while answering "no data" to everything, until they were given the seed check above.

So when you read an example's output, read the output. The exit code only tells you the script did not crash.

That seeded OK line is the check described at the top of this page. If your service refuses the seed, the script stops there instead of printing "no data" thirteen times.

The first four, and the call behind each

#QuestionThe call
1Average CPU load over the last hour aggregate("cpu.load", start=hour_ago_ns(), funcs=["avg"])
2Peak temperature yesterday aggregate("temp.celsius", start=…, end=…, funcs=["max"])
3p99 response time over the past week aggregate("latency.web", start=…, funcs=["p99"])
4Measurements recorded today aggregate("cpu.load", start=day_start, funcs=["count"])

Note question 1 uses nanoseconds (time.time_ns()) because it goes over ZeroMQ. Over HTTP the same query takes seconds. See Client Libraries.

The rest of the catalogue

#QuestionShape
5Is the load rising? two windows compared
6A curve, not a number interval=1m
7Min, average and max per hour three interval=1h calls
8Min, average and max per day three interval=1d calls
9Busiest hour and busiest day bucket, then take the extreme
10Visitors in the last 24 hours funcs=["sum"]
11When did the last reading arrive? limit=1, order=desc, then subtract from now
12All-time numbers no window, plus the median and percentiles
13The same questions over HTTP the curl equivalents, printed

Question 11 is the one worth copying for a staleness check: read the newest point and compare its timestamp against now. A gap means the producer stopped, which is usually the alert you actually want.

The advanced catalogue

question_examples_advanced.py covers what you need once the basics are done: per-series breakdowns when one metric has many tag sets, rates between two timestamps, pattern detection over bucketed data, and data-quality checks such as gaps and duplicates. Its seed data is independent of the first script's, so the two can be run in either order.

Writing data at rate

The producer is the one to reach for when you want to see what the service does under load, and the one to copy when writing a producer in another language — it uses raw zmq and orjson, with no sqtseries import at all.

$ $PY examples/producer.py --port 12500 --rate 1000 --count 100000
# 100,000 points at 1,000/s over the ZeroMQ PUSH socket

# and a burst, to exercise the batch commit
$ $PY examples/producer.py --rate 0 --count 100000 --batch 5000

Then check the accounting. Every accepted point lands in exactly one of persisted, dropped or invalid, so this always balances:

>>> c.admin("stats")["persisted"] - c.admin("stats")["dropped"]

For a properly instrumented run — sustained rate, concurrent query load, memory trend, and a leak verdict at the end — use the rig rather than a single producer:

$ bash scripts/run-stress-rig.sh --duration 300 --rate 2000 --clients 8 --tag baseline

# returns to baseline — no drift, no leak
Why scale_check matters

Subscriber counts come from XPUB events on the wire rather than from polling, so they should be exact. This script is the proof: it churns hundreds of joins and leaves and then asserts the totals match what it created. If a future change broke the accounting, this fails rather than leaving a quietly wrong number on the dashboard.

Timestamps, the practical version

iso_timestamps.py needs no service at all — it opens an embedded database in a temp directory — so it is the fastest thing to run when you only want to settle a timestamp question.

$ $PY examples/iso_timestamps.py
# epoch seconds, ISO with Z, ISO with an offset, naive ISO,
# and nanosecond precision — each written and read back

It also demonstrates the one that catches people: a naive string is read as UTC, not as local time. And a value whose absolute size exceeds 1e12 is read as nanoseconds, which is what lets an ISO timestamp keep its precision through JSON.

Adapting an example to your problem

  1. Start from the closest oneMonitoring, alerting, retention and high-rate ingest each have a script. Read that one rather than starting from the API reference.
  2. Change the metric names and tagsThat is usually the whole change. Keep the tag set small and stable — see Ingestion.
  3. Keep the timestamps rightNanoseconds over ZeroMQ, seconds over HTTP. Copy from a script that already gets it right for your transport.
  4. Set LINGER before you connectOn a PUSH socket, or the last measurement is silently lost. Every producer here does.
