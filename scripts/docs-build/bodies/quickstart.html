What you are about to do

Install the package, start the service, store one measurement, read it back, watch one arrive live, and then leave it running under systemd. Every command on this page was run as written, and the output shown is the real output.

Words used on this page

Service — the running sqtseries run process. It owns the database and all six ports.
Measurement, or point — one value for one metric at one moment.
Metric — the name of the thing measured, like cpu.load.
Tag — a label that splits a metric into dimensions, like host=web1.
Series — one metric with one exact set of tags.
Port — one of six TCP ports. Five are fixed; the sixth, ingest, is chosen at start-up.
Runtime file — runtime.json, written next to the database, recording the pid and the ports actually bound.

Before you start

Two things must be true. Python 3.14 or newer, and the sqtseries package installed. If you use the project virtual environment, point PY at it once and reuse it for every command on this page.

$ PY=/home/iam/devcode/.env/sqtseries/bin/python3
$ $PY --version
# Python 3.14.4 or newer

$ $PY -m pip install sqtseries
$ $PY -m sqtseries --version
sqtseries, version 0.1.0

Check the command list. This is the whole surface — eleven commands, and two global flags:

$ $PY -m sqtseries --help
Usage: python -m sqtseries [OPTIONS] COMMAND [ARGS]...

  sqtseries — embedded time-series database on SQLite + ZeroMQ.

Options:
  --version      Show the version and exit.
  --config FILE  Path to config file (TOML/YAML/JSON).
  --db FILE      Database file to use (overrides config file and env vars).
  --help         Show this message and exit.

Commands:
  backup     Create a consistent VACUUM INTO backup.
  health     Health check (read-only DB probe).
  install    Install the systemd service unit.
  optimize   Optimize query-planner statistics.
  ports      Show active ports.
  run        Start the sqtseries service (foreground).

  stop       Stop the sqtseries service.

Global flags come first

--config and --db belong to the command group, not to a subcommand, so they must come before the subcommand name:

$PY -m sqtseries --config c.toml run   # correct
$PY -m sqtseries run --config c.toml      # wrong: no such option

Look at the ingest port

The log says ingress listening … 12500, even though the configured value is ingestion.port = 12501. With the default ports.auto_detect = true, the ingest port is the first free port in the 12500–12700 range, so it is 12500 and 12501 is never used. The five fixed ports keep their configured values.

$PY -m sqtseries ports
ingest: 12500
query: 12502
stream: 12503
admin:  12504
http:   12505
stats:  12506

Read the ingest port from here, not from your config file. If you would rather it used a fixed port, set ports.auto_detect = false — see Configuration.

2 · Store a measurement

Over HTTP, from the shell. A measurement needs a metric name and a value; tags are optional.

$ curl -X POST http://127.0.0.1:12505/api/v1/write \
    -H "Content-Type: application/json" \
    -d '{"metric":"cpu.load","value":0.42,"tags":{"host":"web1"}}'
{"status":"ok","written":1}

You can send many in one request. The whole array is validated before any of it is stored, so one bad item rejects the batch instead of leaving a half-written one:

$ curl -X POST http://127.0.0.1:12505/api/v1/write \
    -H "Content-Type: application/json" \
    -d '[{"metric":"cpu.load","value":0.51,"tags":{"host":"web1"}},
         {"metric":"cpu.load","value":0.63,"tags":{"host":"web1"}},
         {"metric":"mem.used","value":3.2,"tags":{"host":"web1"}}]'
{"status":"ok","written":3}

Or from Python, over ZeroMQ. The Client is bundled, so there is nothing to install and no URL to configure:

$ $PY
>>> from sqtseries import Client
>>> c = Client()
>>> c.write("cpu.load", 0.77, {"host": "web1"})
>>> c.close()

The default Client ports match the defaults in the table above. If your service moved ports, pass them: Client(ports={"write": …, "query": …, "subscribe": …, "admin": …}).

3 · Read it back

Read every stored point for a metric:

$ curl "http://127.0.0.1:12505/api/v1/read?metric=cpu.load"
{"status":"ok","data":[{"timestamp":1790786862.8571439,"value":0.42},
 {"timestamp":1790786862.8774092,"value":0.51},
 {"timestamp":1790786862.8774092,"value":0.63}]}

Note the timestamps: about 1.79e9. That is epoch seconds, even though they are stored as nanoseconds. Over HTTP both the request and the response use seconds — the conversion is the gateway's job.

Aggregate a whole window in one call:

$ curl "http://127.0.0.1:12505/api/v1/aggregate?metric=cpu.load&funcs=avg,min,max,count"
{"status":"ok","aggregations":{"avg":0.54,"min":0.42,"max":0.77,"count":3.0}}

And from Python, over ZeroMQ. Here the request takes nanoseconds and the reply comes back in seconds:

$ $PY
>>> from sqtseries import Client
>>> import time
>>> c = Client()
>>> now = time.time_ns()
>>> rows = c.query("cpu.load", start=now - 3600*10**9, end=now)
>>> rows
[{'timestamp': 1790786862.8571439, 'value': 0.42}, …]
>>> c.aggregate("cpu.load", start=now - 3600*10**9)
{'avg': 0.54}
>>> c.close()
The units, in one box

This is the mistake that produces an empty result instead of an error, so it is worth stating flatly.

WhereRequest start / endResponse timestamp
HTTP /read, /aggregate seconds, or an ISO-8601 string seconds
ZMQ query socket, Client.query nanoseconds as an integer, or an ISO-8601 string seconds

Sending seconds where nanoseconds are expected asks for a window in 1970 and returns nothing at all — no error, no warning, just an empty list.

4 · Watch values arrive live

Subscribe over ZeroMQ. The iterator yields one dict per measurement, and None as a heartbeat whenever the socket is quiet, so your loop never blocks forever.

$ $PY
>>> from sqtseries import Client
>>> c = Client()
>>> for payload in c.subscribe("cpu.", timeout=1.0):
...     if payload is None:
...         print("(idle)")
...         continue
...     print(payload)
...
>>>>>>> # Ctrl-C to stop
{'metric': 'cpu.load', 'tags': {'host': 'web1'}, 'value': 0.81}
(idle)

From a browser, open the same stream over a WebSocket. * takes everything:

>>> # in a browser console, on the host running the service
>>> ws = new WebSocket("ws://127.0.0.1:12505/ws/subscribe?metric=cpu.")
>>> ws.onmessage = e => console.log(e.data)
>>> ws.onmessage = e => console.log(JSON.parse(e.data))
>>>

The full protocol, including the topic-matching rules and the keepalive frame, is on Streaming.

$ $PY -m sqtseries health && echo "ready" || echo "not ready"

6 · Stop it, and start it for real

run runs in the foreground, so it stops when you press Ctrl-C. stop does the same thing from another terminal, and additionally waits until the process has actually gone — which matters when something is about to rebind the ports.

$ $PY -m sqtseries stop
Sent SIGTERM to pid 178445

For a machine that stays on, install a unit. Generate it with the same config you actually want, so the service does not come back on the defaults after a reboot:

$ $PY -m sqtseries --config ~/sqtseries.toml install
systemd unit installed

$ systemctl --user daemon-reload
$ systemctl --user enable --now sqtseries
$ systemctl --user status sqtseries --no-pager
Running two instances

Give the second one its own database and its own ports. Use --db for the file and a config file for the ports:

[database]
path = "~/.sqtseries/data/second.sqlite"

[ports]
auto_detect  = false
port_offset  = 100

[ingestion]
port = 12601
[query]
port = 12602
[streaming]
port = 12603
[admin]
port = 12604
[http]
port = 12605
host = "127.0.0.1"
[stats]
port = 12606
$ $PY -m sqtseries --config second.toml run

run refuses to start over a database another live instance is serving, and stop refuses to stop an instance whose database is not the one it resolves. Those two refusals are what stop a restart script from killing the wrong process.
