What this example does

A camera posts a stream of analytics — people, vehicles, battery, CPU — as JSON over a WebSocket. Three scripts turn that into stored measurements, a live page you can watch, and seventeen questions you can ask afterwards.

Words used on this page

Pump — the script that subscribes to the camera and writes readings into sqtseries.
Ask — the same script, in a different mode, reading stored data back and answering the catalogue.
Overlay server — a simulator that stands in for a real camera. It serves a page and emits plausible numbers.
Flatten — turning a nested JSON object into many flat metric + value + tags measurements.
camera_id — the tag every measurement carries, so several cameras can share one database.

Why it is worth reading

Nothing in sqtseries knows or cares that the source is a camera. The feed produces ordinary measurements with ordinary tags and goes through the same write path as anything else. That is the point of the example: it is a workload, not a feature, and everything it demonstrates is something you get for free.

The one dependency, and where it is not needed

camera_feed.py in pump mode needs the websockets package, and nothing else. It deliberately does not import sqtseries — it speaks plain HTTP. So it runs from any Python environment, a different virtualenv, or a different machine, as long as it can reach the HTTP port.

$ pip install websockets     # only needed for pump mode

--ask mode needs nothing beyond the standard library, and neither does overlay_server.py beyond what sqtseries already depends on.

How the nested JSON is flattened

A camera sends one message with nesting. sqtseries stores flat triples. So each message becomes eleven measurements, every one tagged with the camera it came from.

// one message from the camera, nested
{
  "current_visible_people": 21,
  "total_detected_people": 237,
  "current_visible_cars": 9,
  "people_last_minute": 21,
  "system_metrics": {
    "batteryPercent": 84.3,
    "cpuUsagePercent": 41.3,
    "cpuTemperature": 62.4
  },
  "detection_overlay_enabled": true
}

// becomes eleven measurements, all tagged camera_id=test_cam_001
traffic.people.current      21     traffic.vehicles.current   9
traffic.people.total        237    traffic.vehicles.total     100
traffic.people.last_minute  21     traffic.cars.last_minute   9
system.battery.percent      84.3   system.battery.temperature 28.5
system.cpu.usage            41.3   system.cpu.temperature     62.4
status.detection_overlay    1      // true -> 1.0, false -> 0.0

Two details worth copying if you write your own flattener:

  • A boolean becomes 1.0 or 0.0. A flag like detection_overlay_enabled is still a measurement, and storing it as a number means you can avg it to find out how often the overlay was on.
  • Strings are skipped. batteryHealth, stats_footer_text and the overlay URLs cannot be numeric measurements, so they are dropped. If you need them, they belong somewhere else — sqtseries stores numbers, and pretending otherwise would cost you the ability to aggregate.

Because every measurement carries camera_id as a tag, ten cameras in one database are ten series per metric — not one blended series. See tags as dimensions for why that matters.

Run it

Four terminals. Start at the top.

Terminal 1 — the camera, or the simulator

With a real camera, point at its metrics WebSocket. With the bundled simulator, start it and note the port it prints — it picks a random free one unless you say otherwise.

$ python3 examples/camera/overlay_server.py
# Overlay server on http://0.0.0.0:58547
# metrics WebSocket:  ws://localhost:58547/ws/metrics
# or pin the port
$ python3 examples/camera/overlay_server.py --port 30080

Environment variables also steer it: TEST_HOST, TEST_PORT, TEST_CAMERA_ID, TEST_PUSH_INTERVAL and TEST_ERROR_INTERVAL. The last one injects errors on a schedule, which is how you test that a client survives a flaky feed rather than only a healthy one.

Terminal 2 — sqtseries

$ sqtseries --config config.toml run

Terminal 3 — the pump

$ python3 examples/camera/camera_feed.py --ws ws://localhost:58547/ws/metrics
connected to ws://localhost:58547/ws/metrics
stored 11 measurements   # per message
…

Leave it running. The faster you want data, the shorter the wall-clock window you need to answer questions over — an hour of data is enough for the catalogue once there is some.

The seventeen questions

These are the questions camera_feed.py --ask actually asks, in the order it asks them. Every one is plain HTTP against the query API — there is no camera support anywhere in the service.

#QuestionHow
1Traffic levels — visible people aggregate(traffic.people.current, avg, min, max, median, p95, p99)
2Busiest hour and busiest day read(traffic.people.last_minute, sum, 1h) and the same at 1d, then take the extremes
3Total footfall aggregate(traffic.people.total, max) — a running total is a max, not a sum
4Day-over-day trend daily footfall sums from read(…, sum, 1d), compared with each other
5Turnover — detected total vs currently visible the two counters side by side; the gap is how long people linger
6Capacity planning — percentile ladder a ladder of percentiles on footfall, to size the site
7Anomaly detection the current hour against the same hour on previous days
8Battery — drain rate and life projection read(system.battery.percent, avg, 1h), then a rate and an extrapolation
9CPU and thermal aggregate(system.cpu.usage) and aggregate(system.cpu.temperature)
10Correlation — footfall against CPU, per hour both bucketed at 1h, then correlated in Python
11Battery drain on busy days against quiet ones split by footfall, then compare the drain slopes
12Feed health — staleness read(…, limit=1, order=desc), then the age of the newest point against the push interval
13Feed uptime — expected against received a count per hour against the expected number of pushes
14Per-camera breakdown the same aggregate for each camera_id
15Monthly projection the observed daily rate extended over a month
16Storage growth read(…, count, 1d), then points per day against the retention window
17Overlay availability aggregate(status.detection_overlay, avg) — near 1 means usually on
Questions 10 and 11 are the interesting ones

A time-series store aggregates one metric at a time. It will not divide two metrics together, and it will not correlate them for you — and that is not a missing feature so much as a consequence of the model. Aggregating each series into hourly buckets and doing the arithmetic over a few dozen rows is cheap, portable, and inspectable.

It is also the honest answer. Correlation computed by a database is a number you cannot explain; correlation computed over two hourly series is something you can.

Watching it live

The stock dashboard shows service health. This shows data — the same measurements as they land — using the public /ws/subscribe endpoint and nothing else. There is no build step and no custom server.

// open examples/camera/overlay.html through any static server, or
// read it and paste the script part into a console on your own page
cat examples/camera/overlay.html

The three lines that matter:

const ws = new WebSocket(
  "ws://127.0.0.1:12505/ws/subscribe?metric=system."   // one topic prefix
);
ws.onmessage = (e) => {
  const m = JSON.parse(e.data);
  if (m.type === "ping") return;      // idle keepalive, not data
  render(m.metric, m.value, m.tags);
};

That is the whole integration. A browser, a topic filter, and a JSON frame.

Why the overlay page is served separately

overlay_server.py runs its own HTTP listener rather than adding a route to sqtseries. That is deliberate: an overlay has to be reachable as a browser source from elsewhere on the network, and putting that on the gateway would add a second, unauthenticated listener to the port that holds your data.

Proving the live path still works

conn_validate.py checks the connection-tracking feed end to end: it joins and leaves clients and ZeroMQ subscribers, and asserts that every change arrives over /ws/connections. It is what the test suite runs, so a change that broke connection tracking fails a test rather than quietly degrading the dashboard.

Adapting it to your own source

The flattener is about thirty lines and is the only part specific to a camera. Everything after it — the writes, the questions, the live page — is generic.

  1. Point at your sourceAny WebSocket, HTTP poll, MQTT topic or file tail works. Keep the pump separate from sqtseries and it stays a five-line client.
  2. Flatten to numbersOne metric name per leaf, booleans as 1.0 and 0.0, strings skipped. Decide your tag set here and keep it small and stable — it is permanent.
  3. Write in batches over HTTPSend an array of measurements per message. It is validated as a unit, so a bad item rejects the batch instead of leaving a gap.
  4. Ask the catalogueEvery question above is one HTTP call. Replace the metric names and they work unchanged.

The higher-rate alternative is to swap the HTTP write for a ZeroMQ PUSH socket — same JSON, no reply, and it does not block on a reply. Everything downstream is identical, so this is a one-function change in the pump.
